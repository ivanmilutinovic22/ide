Preserving [ai] Tags & Automatic Agent Detection

How a lossy serializer silently stripped every AI tag from the config, and why most windows no longer need the tag at all.

[ai] tag
A marker on a window template that opts the window into agent-status tracking (cooking ● / awaiting input ◆).
window spec
The one-line text form used in edit dialogs: name [tag]=cmd|cwd; …
KnownTools
The set of process names recognised as AI-agent CLIs (claude, opencode, tuai, …).

1 · The Bug: a Lossy Round-Trip

Tags live in the config as a proper field — WindowTemplate.Tags. But every edit dialog works on the text form of the windows. Opening the dialog serializes the structs to a string; saving parses the string back. The serializer, formatWindowSpec, emitted name, command, and working directory — and never the tags.

1
Config holds {Name: "agent", Cmd: "claude", Tags: ["ai"]}
2
Press e to edit — form pre-fills via formatWindowSpec → agent=claude The [ai] is already gone here; the user sees nothing wrong.
3
Press Enter to save — parseWindowSpec reads it back → Tags: nil written to config.
4
Restart the session — restart faithfully rebuilds from config, but the config no longer has the tag. Restart was never the culprit; it preserved exactly what the edit had already destroyed.

The same round-trip sits under template editing, so a template edited even once lost its tags — and every environment created from it afterwards inherited the loss. That is why "creating a session from a template" appeared broken too.

The fix

formatWindowSpec now emits tags right after the name, in the exact syntax the parser already accepts:

for _, t := range w.Tags {
    if t = strings.TrimSpace(t); t != "" {
        name += " [" + t + "]"
    }
}
// "agent [ai]=claude|./api" — parses back to the identical struct

A regression test round-trips structs → spec → structs and asserts deep equality, so the serializer and parser can no longer drift apart silently.

2 · The Second Leak: Tags Hiding in Names

The built-in default window was defined as {Name: "ai-assistant [ai]", Cmd: "opencode"} — the tag embedded inside the name string, where HasTag never looks. Older user configs carry the same pattern.

Two changes close this:

  • The default is now a proper struct: {Name: "ai-assistant", Cmd: "opencode", Tags: ["ai"]}.
  • normalizeWindows in internal/config runs on every load and migrates: any [tag] token found in a window name is lifted into the Tags field (case-insensitively deduplicated) and stripped from the name.
Self-healing: existing environments.json files need no manual edit — the migration happens transparently the next time the app reads the config.

3 · Automatic Recognition — No Tag Needed

A window now counts as an AI window if any of three signals fires, checked in this order:

signalexamplewhen it helps
tag template has [ai] agent [ai]=zsh Explicit opt-in, e.g. a shell window where you sometimes launch an agent.
cmd template command is a known CLI agent=claude New. Recognised instantly at session creation — no tag, no waiting for polling.
process live foreground process is a known CLI $ opencode ↵ Ad-hoc: you start an agent by hand in a plain window. 
// internal/ui/agent_status.go
func (m Model) isAIWindow(env config.Environment, windowName, currentProcess string) bool {
    if tmpl, ok := findWindowTemplate(env, windowName); ok {
        if HasTag(tmpl, "ai") || isAIToolProcess(tmpl.Cmd) {
            return true
        }
    }
    return isAIToolProcess(currentProcess)
}

The same three-way check was applied to the two other detection sites that had their own logic: the 500 ms polling-eligibility loop in commands.go and the search popup's one-shot status pass in search.go.

Expanded KnownTools

Detection matches the last path component of the foreground command, case-insensitively, arguments stripped — so /usr/local/bin/claude --resume matches claude. Newly added:

One transitional quirk: sessions started before the fix have tmux windows literally named ai-assistant-[ai]. The cleaned-up template no longer matches that name, so tag/cmd detection misses — but process detection still catches the running opencode, and a session restart recreates the window with the clean name.

2 · The call path, end to end

2.1 Boot

  • main.main → cmd/run.Dispatch()
  • Dispatch reads os.Args[1:], handles --help / --version, then branches:
    • first arg is in cli.Subcommands (env, template) → cli.Run(args)
    • --search → run.Search()
    • otherwise → run.Main()

2.4 Search popup path

  • run.Search → ui.NewSearchModel() → a leaner Bubble Tea model used by the tmux prefix+a keybinding.
  • SearchModel reads the same config + live tmux data, applies fuzzyMatch from fuzzy.go, and on Enter shells out to attach the chosen window.

3 · Where the layers split

  • Side-effecting shells: internal/tmux (exec.Command "tmux …"), internal/terminal (raw tty), internal/config (filesystem).
  • Pure logic: internal/layout, internal/theme, internal/agentstatus, internal/ui/fuzzy. These have unit tests; the side-effecting layers don't.
  • State + glue: internal/ui. Everything that touches Model state lives here. The reason agent_status.go / themes.go are shims over their pure cousins is so the bulk of the package doesn't get rewritten as the leaf packages evolve.

4 · Tmux session naming convention

tmux.SessionName("prod") → ide-prod. This is the contract between the TUI list and the live tmux server: the UI knows a session belongs to the tool because the name starts with ide-, and it can map an environment row to its session by name without storing a tmux ID.

5 · Config file as single source of truth

Both the CLI and the TUI mutate ~/.config/ide/environments.json via internal/config. There is no in-memory daemon — the TUI re-reads on focus and after every write. That's why config is the most-imported package after ui.

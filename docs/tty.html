ide — PTY & embedded terminal

How internal/ui/terminal.go opens a real terminal inside the TUI, where the bytes flow, and whether the same path could replace the polled tmux capture-pane preview.

The PTY package

github.com/creack/pty v1.1.24 — the de-facto Go pty library, a thin wrapper around the OS's posix_openpt / grantpt / unlockpt dance. It gives us pty.StartWithSize(cmd, *pty.Winsize), which forks the child onto a new pseudo-terminal master/slave pair and returns the master *os.File (ptmx). Companion library: github.com/hinshun/vt10x — a pure-Go xterm-ish virtual terminal that consumes the master's output and maintains an in-memory screen grid.

1 · What "attach to terminal" actually means here

When you press Enter on a window row the TUI doesn't shell out and hand the terminal to tmux attach — that would unmount Bubble Tea and replace the screen. Instead, ide stays in control of the screen and runs tmux attach-session as a child process wired to a pseudo-terminal it created itself. Everything that child writes to its "screen" lands in our process as bytes we can read; everything you type gets fed back to it as bytes we write.

A pseudo-terminal (PTY) is two file descriptors that look like a real serial line to the kernel: the master end is ours, the slave end becomes the child's stdin / stdout / stderr and controlling tty. That's why programs running inside it — bash, vim, htop, claude, tmux — behave exactly as if you had launched a real terminal: isatty() returns true, tput cols works, SIGWINCH fires on resize, and ANSI escapes come back correctly.

2 · The byte path, top to bottom

tmux attach-session
Child process on the PTY slave. Writes ANSI to its "screen", reads keypresses from its stdin.
user keystrokes
Bubble Tea tea.KeyMsg in the host TUI.
PTY master (ptmx)
creack/pty.StartWithSize returned this *os.File. Read = child's stdout. Write = child's stdin.
keyToBytes(key)
Maps bubbletea key names → raw bytes: "enter"→\r, "ctrl+a"→0x01, arrows → CSI sequences, "alt+x"→ESC x.
vt10x.Terminal
In-memory screen grid. vt.Write(buf) parses ANSI, updates cells with FG/BG/attrs, moves cursor.
ptmx.Write(data)
Bytes go straight to the child's stdin via the PTY master.
EmbeddedTerminal.Render
Walks cells, emits SGR runs (cached per color), returns an ANSI string Bubble Tea draws as the right pane.
updateTerminalMode
Catches ctrl+q as the local "exit" escape; everything else is forwarded.

Solid arrows = data flowing out of the child into our screen. Dashed arrows = keystrokes flowing in from the host TUI to the child.

3 · The pieces, mapped to code

StepCodeWhat happens
Make a virtual screen vt10x.New(WithSize(cols,rows)) In-memory cell grid sized to the right pane. No real fd yet.
Open PTY + fork child pty.StartWithSize(cmd, &Winsize{…}) Allocates master/slave, dups slave onto child's stdio, sets it as controlling tty, returns the master *os.File (ptmx). One call instead of the 6 syscalls you'd otherwise write.
Inform the child of size pty.Setsize(ptmx, &Winsize{…}) Used by Resize. Triggers SIGWINCH in the child so tmux, vim, etc. redraw at the new dimensions.
Drain output → screen readPTYCmd(et) A tea.Cmd that blocks on ptmx.Read, feeds bytes to vt.Write, returns ptyReadMsg{}. Re-issued from Update on every msg → continuous loop.
Render screen → ANSI EmbeddedTerminal.Render Walks the visible grid, batches SGR escapes only when style changes, paints the cursor as \x1b[7m (reverse). Per-color SGR strings are memoized in fgSGR/bgSGR (capped at 4096 entries).
Forward keystrokes WriteInput(keyToBytes(key)) keyToBytes maps Bubble Tea's key names back into the raw bytes a terminal would actually send (CSI for arrows, single byte for ctrl+letter, ESC-prefix for alt+letter).
Tear down EmbeddedTerminal.Close Closes ptmx (child gets EOF on stdin), kills + waits the child process. Idempotent via closed flag.

4 · Why we run tmux inside the PTY instead of bash directly

The child we exec is tmux attach-session -t ide-<env>:<window>, not the window's actual command. That keeps two big invariants:

  • The tmux server is still the source of truth for what's running — if you detach from ide, the session keeps living, and external tmux a -t ide-prod still works.
  • Window state (scrollback, copy-mode, multiple panes) is preserved across attach/detach cycles. The vt10x emulator just paints whatever tmux happens to draw — it doesn't have to understand pane splits.

5 · Could we use the same PTY path for the right-pane preview?

Right now the preview is the polled path: capturePaneCmd in internal/ui/commands.go shells out to tmux capture-pane -p -e -t target on a tick, stores the result as m.previewContent, and renderPreviewRows in view.go slices the last N lines for display.

Current: tmux capture-pane polling

  • Snapshot of the screen at the moment tmux's renderer last wrote to the pane.
  • One tmux fork per tick per selected window.
  • Inherits whatever tmux decided about wrapping, colors, cursor — including tmux's reflow if the pane width differs from ours.
  • No cursor; -e gives ANSI but only the visible region, no live cursor.
  • Trivially correct for SSH, attaching from another machine, mosh, etc. — tmux already handles it.
  • Idle CPU = wake up, fork, read, parse, render.

Proposed: PTY-driven preview

  • Reuse EmbeddedTerminal in a "passive" mode: open a PTY running tmux attach -r (read-only) for the selected window, but never WriteInput.
  • Output is processed by vt10x continuously, so the preview matches what's actually on screen byte-for-byte at this exact moment, cursor included.
  • No per-tick forks — one persistent process per selected window, fed by a single goroutine read loop.
  • Reflow happens in our vt10x instance at our pane width; we control the geometry instead of inheriting tmux's.
  • Switching the selection means tearing down one attach + starting another. The cost of "show me window X" is the attach handshake, not a one-shot capture.

5.1 · Where it would actually be more precise

  • Cursor visibility — capture-pane doesn't tell you where the cursor is. The PTY path already paints it (we do this in terminal-mode today).
  • Live frame for animations — progress bars, spinners, htop: capture-pane shows whatever frame tmux happened to be on at poll time, with no guarantee we caught the latest one. A persistent reader sees every frame.
  • Wrapping — if our right pane is 60 cols and the tmux session is 120 cols, capture-pane returns 120-col lines and we either truncate or scroll. With our own vt10x we open the PTY at 60 cols and the producer reflows.
  • Color fidelity — we already do the SGR translation ourselves; we don't depend on tmux capture-pane -e's subset of escapes.

5.2 · The trade-offs to know about

  • One PTY per previewed window. Cheap, but it means N file descriptors and N tmux children if you ever preview multiple at once. Today, "selected window" is single, so this is one.
  • Tmux clients see us. tmux list-clients will show an extra read-only client for the previewed session — visible in display-message, can affect tmux's aggressive-resize.
  • Geometry coupling. Tmux clients negotiate a session size as the minimum of all attached clients. A small preview pane could shrink the session for any real attach. Workaround: client flag -x/-y + per-window window-size manual, or attach -r + aggressive-resize on with per-window sizes.
  • Read-only attach is per-session, not per-window. tmux attach -r -t ide-prod:editor attaches you to the session and selects that window, but switching the previewed window means either sending a tmux command or re-attaching. Sending select-window via the attached client would also move real attaches; safer is detach + re-attach with a new -t.
  • Lifecycle complexity. Today the preview state is purely cached strings — losing it is free. A persistent PTY has to be torn down on window change, on quit, on session-kill events; EmbeddedTerminal.Close already does this for terminal-mode and would need to be driven from the preview state machine too.

Pragmatic answer

Yes — the PTY path is strictly more precise (live cursor, reflow at our width, every animation frame). The cost is a persistent tmux client per previewed session and a small piece of lifecycle code to detach/re-attach when the selected window changes. The infrastructure already exists in EmbeddedTerminal: a "passive preview" mode is roughly "open the same way terminal-mode does, just drop WriteInput on the floor and don't switch focus to it". The honest blockers are tmux's session-size negotiation and the lifecycle bookkeeping, not the rendering pipeline.

6 · Sketch of the migration

// new state on Model
previewTerm *EmbeddedTerminal  // nil unless a window is selected
previewKey  string             // session:window currently attached

// when selection changes (or session goes live)
func (m *Model) refreshPreview() tea.Cmd {
    key := session + ":" + window
    if m.previewKey == key { return nil }
    if m.previewTerm != nil { m.previewTerm.Close() }
    et := newEmbeddedTerminal(previewCols, previewRows)
    // -r = read-only, -x/-y pin client size so we don't resize the session
    cmd := exec.Command("tmux", "attach-session", "-r",
        "-t", session + ":" + tmux.SafeWindowName(window),
        "-x", strconv.Itoa(previewCols),
        "-y", strconv.Itoa(previewRows))
    // ... pty.StartWithSize as in Attach, but cache cmd on et
    m.previewTerm = et
    m.previewKey  = key
    return readPTYCmd(et)
}

The preview paints a coloured rectangle

It isn't a bug in our renderer; it's the contents of tmux's pane buffer being shown faithfully. Here's what's happening and how to soften it.

pane buffer
tmux's per-pane 2-D array of cells; each cell holds a glyph and an SGR style.
capture-pane
tmux command that serialises the pane buffer back into ANSI bytes.
styled space
a cell whose character is ' ' but whose style is not default — e.g. a space with a yellow background.
vt.Emulator
The off-screen terminal we replay the bytes into to get our preview render.

2 · Why tmux sends "styled spaces"

When vim opens a netrw buffer with a coloured theme, it doesn't just paint the glyphs. To get a clean rectangular feel, it issues an "erase to end of line" with the BG colour still active. Tmux's pane buffer dutifully records each of those cells as space + yellow BG.

If you ask tmux to dump the pane (capture-pane -e), it walks every cell and emits its colour, including the trailing styled spaces. The emulator we feed those bytes to replays them exactly. The render now sees a row full of yellow-backed cells, so the rendered ANSI carries yellow all the way across.

The live path never sees those bytes. attach-session hands us the live application, which only paints what it needs to update. The columns past .cache/ in a redraw are usually untouched, so the cells stay at default style, and the host terminal background shows through.

vim → tmux pane buffer (one row, width = 20) ┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐ │.│c│a│c│h│e│/│ │ │ │ │ │ │ │ │ │ │ │ │ │ └──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┴──┘ └── glyphs ──┘└─────────── styled spaces ─────────────────┘ (space char, yellow BG — the netrw theme) capture-pane -e emits, roughly: ESC[48;5;229m .cache/ ESC[0m └──── trailing yellow ────┘
The cell buffer is honest. A "yellow space" is genuinely a cell on the screen. Tmux can't tell whether vim meant "fill the row" or "I just want this glyph"; both look identical at the cell level.

3 · The four-stage chain

1
vim writes ".cache/" with EL (erase to end of line) under yellow BG. Most TUI apps do this to get a clean coloured panel without explicitly painting every cell.
2
tmux records each affected cell into the pane buffer. Including the trailing spaces — they all carry the yellow BG SGR.
3
capture-pane -e serialises every cell back to ANSI. No heuristic to drop "trailing decorative space" — tmux can't know it's decorative.
4
vt.Emulator replays the bytes, Render() emits ANSI with yellow across the row. From the emulator's point of view, the row genuinely has yellow cells. Honest behaviour.

4 · Three ways to soften it

None of these recover what vim "meant"; they each pick a trade-off between fidelity and blending.

Option A — Trim trailing styled spaces

After em.Write(raw), walk each row in the cell buffer and find the rightmost cell whose glyph is not a space. Reset every cell to the right of it back to default. Then call Render().

for y := 0; y < rows; y++ {
    last := -1
    for x := cols - 1; x >= 0; x-- {
        c := em.CellAt(x, y)
        if c != nil && c.Content != " " {
            last = x; break
        }
    }
    for x := last + 1; x < cols; x++ {
        em.SetCell(x, y, &uv.EmptyCell)
    }
}
  • keeps mid-line BGs (status bars where text sits between styled spaces), inline syntax highlight BGs.
  • breaks full-row coloured borders that don't end in a glyph (a fzf preview box drawn with spaces would lose its right edge).

Option B — Strip all backgrounds

Walk every cell, clear its style's BG field, keep FG / bold / italic / underline. The preview becomes "text-only colour".

  • cleanest blend across every host theme. Preview always melts into the host BG.
  • flattens tmux status bars, vim's mode line, syntax BGs (diff blocks, search highlights), mc panels, htop bars — all lose their backgrounds.

Option C — Leave it alone

The current state. The preview faithfully reproduces what tmux says the pane contains. If you want the yellow gone, change your vim/tmux theme.

  • honest — what you see in the preview matches what attaching will show.
  • ugly when an app paints a coloured panel that's smaller than the preview rect.

5 · The recommendation, and what it costs

Option A is the smallest hammer. It targets exactly the failure mode in image #7 (vim filling the row with decorative yellow spaces) while preserving the cases where colour matters (something sits between text on the same row).

The known regression is full-row decorative borders. fzf's preview pane, midnight-commander's panels, and a few status bars that don't right-anchor a glyph will lose their right edge. In practice these are minority cases for our preview rectangle, which is usually showing a shell or editor.

What we will not do: reintroduce a detectPreviewBG heuristic that scans capture bytes for "the dark colour" and remaps it. That path was deleted last refactor; the trade-off here is per-row, not whole-pane.

6 · Footnote on why "set the default BG to host" doesn't work

A tempting fix: tell the emulator "the default background is the host terminal's colour" so styled-yellow spaces that match the host blend out. Two reasons it doesn't help:

  • We don't know the host BG. The terminal doesn't reliably report it; we'd be guessing and getting it wrong on every theme switch.
  • The yellow cells aren't claiming to be "default" — they have an explicit SGR 48;5;229. Setting the emulator's default to host doesn't suppress an explicit colour; it just changes what unstyled cells look like, which is already what we want.

1 · What changed at a glance

Two render paths used the embedded VT emulator. Both still exist, both still look the same, but the path through them is now much shorter.

dropped / replaced new or unchanged terminal / vt tmux / pty UI render

Before

  • hinshun/vt10x for both renderers
  • Per-cell SGR walk in Render(width,height), two memoised map[Color]string caches
  • Six vtAttr* bitmask constants reverse-engineered from vt10x internals
  • detectPreviewBG scanned capture-pane bytes for the darkest SGR 48 and reinjected it after every \e[0m
  • Preview content lived as raw bytes in m.previewContent; the view did all the rendering work each frame

After

  • charmbracelet/x/vt everywhere — Emulator.Write + Emulator.Render
  • Render body collapses to strings.Split + ansi.Cut per line
  • No bitmasks, no SGR caches, no glyph walker
  • No BG heuristic. Untouched cells emit no BG escape, so the host terminal background shows through naturally
  • Preview is rendered in the capture goroutine; the view just bottom/left-crops and pads with empty strings

The render body — after

rendered := et.vt.Render()
if rendered == "" { return "" }
lines := strings.Split(rendered, "\n")
if len(lines) > height { lines = lines[:height] }
for i, line := range lines {
    if ansi.StringWidth(line) > width {
        lines[i] = ansi.Cut(line, 0, width)
    }
}
return strings.Join(lines, "\n")

What we lost: the inline cursor block

The old renderer drew a reverse-video block at (cursor.X, cursor.Y). x/vt's Render doesn't paint a cursor glyph, and the emulator doesn't expose CursorVisible publicly. Acceptable trade — tmux's status line and the application itself (vim, fish, htop) draw their own cursor; the preview pane only loses the synthetic block.

capturePaneCmd, after

func capturePaneCmd(session, window string) tea.Cmd {
    return func() tea.Msg {
        process := tmux.CurrentProcess(session, window)
        cols, rows, err := tmux.PaneSize(session, window)
        if err != nil || cols <= 0 || rows <= 0 {
            return panePreviewMsg{session: session, window: window, process: process}
        }
        raw, _ := tmux.CapturePane(session, window)
        em := vt.NewEmulator(cols, rows)
        em.Write([]byte(raw))
        return panePreviewMsg{
            session: session, window:  window,
            content: em.Render(),
            process: process,
        }
    }
}

4 · The accidental complexity we deleted

The old code did a lot of work to paper over one limitation: capture-pane output isn't padded to a rectangle, so when the preview area was wider than the longest line the right edge revealed whatever lipgloss painted behind it. The fix was a heuristic plus a string-rewriter. With the emulator owning the rectangle, the symptom disappears.

Why the host BG now blends

x/vt's Buffer.Render walks cells and only emits a style change when a cell has a non-zero Style. Empty cells (default pen) write a plain space with no SGR, so the host terminal background shows through. Tmux's status bar and any TUI that paints its own BG still come through coloured; untouched cells stay transparent. That removes the entire reason detectPreviewBG existed.

6 · What I couldn't verify here

Manual verification deferred

The agent box doesn't have a display, so checks (a)–(h) in the task — preview blends with light & dark hosts, vim/htop colors, narrow/tall/wide pane crops, attach/detach round-trip — were not run. Static checks did pass: go fmt ./…, go vet ./…, go build . all clean against the new module graph.

What to look for first

  • Light terminal background. Open the app under a Catppuccin Latte (or Solarized Light) host. The preview rect should fade into the page; if you see a dark band around the bottom-left content, vt.Render is emitting BG for empty cells and we need to investigate cell zero-style detection.
  • Wider host pane than preview rect. Long lines should clip cleanly; the column at contentWidth − 1 should not bleed SGR into the right-side gap.
  • Cursor position in vim. Vim's own cursor block should still show — the lost block was the synthetic reverse-video one, not the application's.

7 · Structural surprises from x/vt

Two API shape differences that nudged the design beyond the brief:

  • x/vt doesn't expose CursorVisible() — visibility is tracked internally but only reachable via a Callbacks.CursorVisibility hook. We dropped synthetic cursor rendering rather than register a callback for what's essentially decoration.
  • The brief mentioned cellbuf.Render(term.Screen()). The current x/vt exposes Terminal.Render() string directly (which walks the underlying ultraviolet buffer), so we use that — same result, one fewer import.

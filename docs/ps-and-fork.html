fork, exec, and ps -A

Why running a subprocess is expensive, what the kernel actually does, and why one ps -A beats sixty pgreps.

1 · The fork+exec dance

On Unix there is no system call that says “run this other program.” The only way to start one is a two-step ritual:

parent process child process kernel target program syscall
Go program (parent)
calls cmd.Run() which invokes syscall.ForkExec under the hood.
fork()
request to the kernel: “duplicate me.”
kernel
allocates a new PID; copies process metadata (page tables, fds, signal handlers).
parent (unchanged)
fork returns the child’s PID. Parent waits with cmd.Wait().
child copy
identical memory to the parent. fork returns 0 here — that’s how it knows it’s the child.
exec(“ps”, …)
replace this process’s memory with the ps binary.
ps (runs, prints, exits)
parent’s Wait() unblocks, collects exit code and stdout.

Why the dance?

If Go called exec("ps") directly without forking, your Go program would become ps and never come back. Fork gives you a throwaway copy to spend on the new program; the original keeps running.

2 · Why fork is expensive (and especially on macOS)

Even with all the optimisations modern kernels do, fork is not free:

  • Page tables. The kernel duplicates the parent’s page-table entries so the child sees the same memory. Copy-on-write means the underlying pages aren’t physically copied until written, but the bookkeeping is per-page.
  • File descriptor table. Cloned. So is the signal handler table, working directory, controlling tty, umask, …
  • kqueue / epoll / pid maps. The Go runtime has signal handlers, GC state, and an internal scheduler that all have to be in a consistent state at the moment of fork.

The macOS tax

XNU (macOS’s kernel) does more work per fork than Linux:

  • Stricter parent/child isolation by default — fewer shared structures.
  • The fork implementation has to negotiate with the macOS security subsystems (sandbox, entitlements) which each get a chance to inspect the new process.
  • macOS prefers posix_spawn for spawning new programs. It combines fork+exec into one call and skips much of the dup-then-throw-away work. Go uses it on macOS where it can — but for the explicit fork-then-do-something case, you pay full price.

Rough order of magnitude

A fork+exec of a small program on a recent MacBook is on the order of 1–5 ms of wall time and ~10 ms of CPU. Doing that 60 times every 500 ms shows up as constant background CPU. Doing it once doesn’t.

3 · What ps -A returns

ps -A (also spelled ps -e) dumps the entire system process table in a single call. Without flags it shows four default columns:

  PID TTY           TIME CMD
    1 ??         0:42.13 /sbin/launchd
  123 ??         0:00.05 /usr/sbin/syslogd
  456 ttys001    0:12.30 -fish
  789 ttys001    0:00.81 nvim
 1011 ttys002    0:00.02 ps -A
 ...

With -o you pick exactly the columns you need. The code in internal/tmux/tmux.go uses:

ps -A -o pid= -o ppid= -o %cpu= -o state=

The trailing = on each format specifier suppresses that column’s header row, so the output is pure data:

    1     0   0.0 S
  123     1   0.0 S
  456   123   0.1 S
  789   456  12.4 R
column meaning why we need it
pid process ID identifies the row, and is what tmux gives us for the pane shell.
ppid parent process ID the edges of the process tree — lets us reconstruct descendants without pgrep.
%cpu recent CPU percentage the metric we sum to decide if an AI agent is “cooking.”
state R, S, D, Z, T … one of these in the subtree being R means something is actively running.

State codes you’ll see

Rrunning (or runnable — on a CPU or waiting for one)
Ssleeping (most processes most of the time)
Duninterruptible sleep (disk wait)
Zzombie (exited, parent hasn’t reaped)
Tstopped (e.g. by SIGSTOP)

4 · Walking the tree in memory

Once you have the full table, building the parent → children map and walking the subtree is just hash-table work — no subprocesses, no syscalls.

ps table snapshot child map (ppid → []pid) shell / agent root descendants
snapshotProcesses()
runs ps -A -o pid= -o ppid= -o %cpu= -o state= once, parses each line into a procRow, returns map[int]procRow.
buildChildMap(rows)
groups every row by its ppid. Result: map[int][]int — for any PID, look up its direct children in O(1).
shellPID (pane root)
tmux display-message -p #{pane_pid} gave us this. Push it onto a stack and walk down.
descendants
iterative DFS using the child map. Sum cpu; flip hasRunning if any state is R.

The walk itself is the boring part — a stack, a visited set, a couple of accumulators:

stack := []int{shellPID}
for len(stack) > 0 {
    pid := pop(stack)
    if visited[pid] { continue }
    visited[pid] = true

    if row, ok := rows[pid]; ok {
        totalCPU += row.cpu
        if row.state == "R" { hasRunning = true }
    }
    stack = append(stack, children[pid]...)
}

5 · Old vs new — the actual diff

The bug the review caught: this loop was running 500 ms apart for every AI window, each iteration doing the wrong thing N times.

Before — fork-bomb per poll

// for each AI window per tick:
shellPID := tmux display-message ...

// recursive walk:
pgrep -P shellPID          // fork+exec
for each child:
    ps -p child -o %cpu,state  // fork+exec
    pgrep -P child         // fork+exec
    for each grandchild:
        ps -p ...          // fork+exec
        pgrep -P ...       // fork+exec
        ...

For a tree of N descendants: roughly 2N forks. Times M AI windows. Twice a second.

After — one ps -A per poll

// once per tick, total:
rows := snapshotProcesses()       // ONE fork+exec
children := buildChildMap(rows)   // pure Go

// per AI window:
shellPID := tmux display-message ...
walk(shellPID, rows, children)    // no syscalls

One subprocess per tick, regardless of tree size, AI window count, or descendant depth.

Concrete numbers

scenario before after
1 AI window, 10 descendants ~20 forks / tick 1 fork / tick
3 AI windows, ~10 descendants each ~60 forks / tick 1 fork / tick
3 AI windows × 2 ticks/sec × 60s/min ~7,200 forks / min 120 forks / min

Why it doesn’t matter that ps -A returns “too much”

ps -A dumps every process on the system — typically a few hundred lines. Parsing that in Go is a tight loop over a byte buffer: trivial compared to one fork. Trading one expensive syscall for ~500 cheap field-parses is always a win.

6 · Why not filter ps directly, or pipe to grep?

A natural reaction to “ps -A returns the whole system table” is: can’t we just ask for the rows we care about? Sometimes yes — but not here. The reason is a chicken-and-egg in how Unix stores parent/child relationships.

What you can do

ps takes a PID list:

ps -p 54321,54322,54323 -o pid=,ppid=,%cpu=,state=

One fork, tiny output, exactly the rows you wanted.

Why it doesn’t work for us

You have to know the PIDs upfront. We only know one: the pane’s shell PID from tmux display-message -p #{pane_pid}. The whole job is to discover the descendants. Catch-22:

The dependency cycle

  • To filter ps → need descendant PIDs.
  • To get descendant PIDs → need to walk parent→child edges.
  • To walk edges → need ps output.

The kernel has no “give me PID X and all its descendants” syscall. The parent/child relationship is stored backwards: every process records its ppid, but no process stores a list of its children. To assemble a subtree you either:

  • Start at X, ask “who has ppid=X?”, recurse. That’s pgrep -P X called repeatedly — the old fork-bomb code.
  • Or dump every row once and invert the index in memory — the current approach.

Why grep doesn’t rescue this

ps -A | grep 54321

Two problems:

  • It filters text. You’d get the row with pid=54321, plus anything that happens to contain “54321” in its command line — false matches galore.
  • More importantly, it doesn’t reveal which other rows are descendants. To find children you’d grep for ppid=54321, then for each match grep again, recursively. Same fork loop, plus a grep per level. Worse than the original.

The trade-off, side by side

approach forks per poll data transferred catch
ps -p <known PIDs> 1 tiny requires knowing the PIDs first
pgrep -P, recursively O(tree size) tiny each fork-bomb (the bug)
ps -A | grep 2 + recursion tiny each text matching, still recursive
ps -A once, walk in Go 1 ~500 rows what we do

Trading a few hundred parsed lines for one fork beats trading zero wasted lines for N forks. The “wasted” parsing happens in the same Go process, in a tight loop over a byte buffer, on a hot CPU cache. That’s not real work.

Where this would be different

Linux has a shortcut macOS doesn’t

On Linux you can read /proc/<pid>/task/<pid>/children — a kernel-maintained list of direct children, no ps, no fork. Walking the tree becomes a series of file reads. macOS has no /proc, so portable code uses ps -A instead.

7 · Recap

  • fork() + exec() is the only way to start another program on Unix. The fork is the “make a throwaway copy” step; the exec is “replace that copy with the target binary.”
  • Each one involves real kernel work — page tables, fd table, signal handlers — and on macOS the per-fork cost is higher than on Linux.
  • ps -A hands you the entire process table at once. With -o pid= -o ppid= -o %cpu= -o state= you get exactly the four fields you need to rebuild the tree, sum CPU, and detect activity — all in memory, in Go, with zero further subprocesses.
  • The fix swapped an O(tree-size × AI-windows) fork loop for a single fork per poll. Same answer; orders of magnitude less work for the kernel.
